# 電圧制御の自動チューニング 引き継ぎ

最終更新: 2026-09-24　／　前提の文書: [`HANDOFF_VOLTAGE_CONTROL.md`](HANDOFF_VOLTAGE_CONTROL.md)（特に 5.8〜5.10、6章）

## 1. やりたいこと
- 電圧制御（疑似トルク制御）の足回りで、**最高の加速度・速度が出る閾値・ゲインを自動で見つける仕組み**を作る。
- これまでは「書き込み → 床で動作パターンのテスト → ST-Link で RAM のログを読む → 解析 → 手で値を変える」を1回ずつ繰り返して調整してきた（5.10）。これを自動化したい。
- ユーザーの当初の案: 動作パターンのテストに近いものを数回繰り返し、実行のたびに内部の閾値を更新して、最適な値を見つける。
- **この文書の7章に、案に対する改善点をまとめた。実装の前にユーザーと方針（8章）を決めること。**

## 2. 現状（ブランチ `FW/MainBoard_V26_2_tc`、コミット `d3ce39ec`、push済み）
- 試合の経路（Rock5A からの指令）は電圧制御で動く設定（`ROBOT_USE_VOLTAGE_CONTROL=1`）。**Rock5A の指令で車輪が回り機体が動くことは、2026-09-24 に確認した（機体を浮かせた状態。床での走行は未確認）。11章参照。**
- `main_mode.c` の Rock5A 未接続時の処理は `LocalController_Stop`（止まる）。テストを使うときだけ書き換える。
  - → 段階1（10.3）以後は、動作パターンのテストは ST-Link から開始の指示（`tools/autotune_start.ps1`）を書いたときだけ走る。書き換えは要らない。
- 処理の流れ（1msごと、`OmniDrive_SetVelEx` の電圧制御の分岐、`src/unit/omni_drive.c`）:
  1. 指令 (vx, vy, ω) → `TCS_Update` の S字加減速（加速度・角加速度の上限あり）
  2. 各輪の電圧 = 「その輪の実際の回転数で転がり続ける電圧（center）」＋「超える分（＝トルク）」
  3. 超える分 = FF（表の逆引き＋床の負荷分＋機体加速度×係数を力の配分 `force_alloc` で4輪へ）＋ 機体速度の PI（オドメトリ・ジャイロ）
  4. 超える分を ±`VOLT_TRACTION_LIMIT_V`（トルク上限）と電圧上限 4.9V に収める。先に FF の分を4輪同じ比率で縮め、足りなければ PI の分を縮める。

### 2.2 手動調整で分かったこと（5.10 の要約）
| トルク上限 | 動作パターン13区間の時間 | スリップの割合（区間により） | ユーザーの評価 |
|---|---|---|---|
| 2.0 V | 約23.1 秒 | 11〜66% | |
| 2.4 V | 約20.3 秒 | 28〜64% | 前後左右で「若干」スリップが見える |
| 3.2 V | 約18.4 秒 | 50〜87% | 斜めはかなり良い／前後左右はスリップが目立ちすぎ／旋回で行き過ぎ |
| **2.8 V（確定）** | 約19.2 秒 | 前後左右 58〜69%、斜め 29〜48% | 手動調整はここで確定 |

- 速さとスリップは、はっきり引き換え。**「最速」だけを目的にすると、ユーザーが嫌った 3.2V 側に寄る。** 目的関数にスリップや正確さを入れる必要がある（7章の3）。
- 前後左右は4輪がそろって力を出すのでトルク上限に掛かる前に滑る。斜めは2輪に力が集中し、その2輪がトルク上限に早く掛かって全体が抑えられる。**向きごとに限界が違う**（7章の6）。
- 旋回の行き過ぎは、外側ループが実際の角速度を見ていなかったのが原因で、D項を足して解消（2.0V:0〜13° → 3.2V:28〜37° → PD後 1〜6°）。自動調整でゲインを上げると、同じ種類の問題が別の場所で出うる。
- `is_slipping`（TCS のスリップ判定）は、速度モード用に決めた閾値のまま。電圧制御で強く加減速すると、本当の滑り以外でも立つ可能性がある。**そのまま目的関数に使うと、最適化が判定の癖を突く**（7章の4）。
- 1回ごとのばらつきがある（同じ設定でも旋回区間の時間が 0.9〜1.3 秒）。1回の比較で良し悪しを決めない。

## 4. 制約・注意（前のチャットで実際に踏んだもの）
- **PC にホスト用の C コンパイラ・Python は無い**（`python` は Store のスタブ）。解析は PowerShell 5.1 で行ってきた。
  - スクリプトは **UTF-8 BOM 付き**で保存（BOM なしは CP932 として読まれ、日本語コメントが次の行を飲み込む）。
  - 変数名は大文字小文字を区別しない（`$h` と `$H`、`$s` と `$S` が衝突した）。
  - `@(a, b/1000.0)` はカンマの方が先に結び付く。割り算は括弧で囲む。
  - 正規表現の `{4}?` は「省略可」ではなく最短一致。
- ビルドは PowerShell で `make -j`（Git Bash は TEMP の問題で gcc が失敗する）。書き込みはユーザーが行ってきた。
- **ST-Link を挿したままだと WheelUnit からの受信が途切れやすい**（5.2、原因未調査）。走行中の ST-Link は抜いてきた。そもそも機体が 2〜3m 動くので、ケーブルをつないだまま走らせるのは難しい。
- 走行の場所: 動作パターン（1.5倍）で、スタート位置から前に約2.0m、後ろに約0.5m、左右に約2.0m。
- WheelUnit の保護: **+5.0V ちょうどが1秒続くと出力を止める**（正側のみ）、60℃超で停止（50℃で復帰）、電源15V未満で停止。自動で何度も強く走らせると、モータの温度と電池電圧が変わっていく。
- 安全: テストは `main_mode.c` の「Rock5A 未接続時」の分岐から呼んでいる。**戻し忘れると、Rock5A 未接続のときに機体が勝手に動く。** 自動調整を入れるなら、明示的な操作でだけ始まるようにする（7章の8）。

## 5. 当初の案（ユーザー）

## 6. 案の良いところ
- ケーブルも通信の拡張も要らない。今のテストと RAM ロガーをそのまま使える。
- 動作パターンは閉ループで原点に戻るので、続けて何回か走らせられる。

## 7. 改善点（提案）
1. **「測って決められる値」と「探すしかない値」を分ける。** 多くの値は物理量で、探索しなくても専用の走行で直接測れる。
   - 例: トルク上限を1回の走行の中で少しずつ上げ、向きごとに滑り始める所を見つける（=向きごとの床の限界）。実際に出せた加減速度から `VOLT_MODE_MAX_ACCEL` と外側ループの想定減速度を決める。旋回も同じ。
   - 探索に残すのは、速さと滑りの引き換えのような、ユーザーの好みで決まる少数の値だけ。次元が減るほど、少ない走行回数で決まる。
2. **試合で効く値だけを調整する。** 外側ループ（`kPosKp` など）はテスト専用で、試合では Rock5A が経路を作る。外側ループは固定し、内側（トルク上限・S字の上限・FF・PI）だけを動かす。さらに、見つけた加速度の上限を **Rock5A 側の経路計画の加速度の上限にも反映**しないと、試合では活きない。
3. **目的関数は「最速」ではなく「制約付きの最速」にする。** 例: 区間の時間を最小化。ただし、止まった位置のずれ ≤ 5cm、向きの行き過ぎ ≤ 5°、進む向きからの外れ ≤ ○cm、安全停止なし。スリップの割合はペナルティか上限にする。重みや上限は、ユーザーの評価（2.4V=許容、3.2V=滑りすぎ、2.8V=確定）に合うように決める。
4. **測り方そのものを信用しすぎない。** 位置も速度も車輪のオドメトリで、滑るほど狂う。最適化は測定の誤りを突きやすい（「着いた」とオドメトリが言っても実際は行き過ぎている、など）。
   - 最善: **SSL-Vision（天井カメラ）で実際の位置を測る。** 使えるかユーザーに確認する。
   - 次善: 数回ごとに実際の止まった位置を人が測る、IMU の積分と照合する、スリップ判定の閾値を電圧制御用に見直す。
5. **ばらつきに強くする。** 1つの設定を1回で評価しない（2〜3回、または区間をまとめて平均）。探索は少ない回数で済む方法（1〜2変数ずつの黄金分割探索や座標探索）から始める。
6. **向きごとの限界を持たせる。** 今は全方向で同じトルク上限・加速度上限。前後・左右・斜めで限界が違うことが分かっているので、向きごとの加速度上限（楕円の摩擦円など）を持たせると、斜めを削らずに前後左右の滑りを減らせる可能性がある。
7. **会場で短時間に走らせ直せる「較正手順」として作る。** 大会のフィールド（カーペット）は練習の床とグリップが違うので、今の床で決めた値はそのまま使えない。狭い場所・数分で終わる手順にしておくと価値が大きい。長期的には、固定の閾値ではなく、走行中に滑りを見てトルクを絞る本来の TCS（実行時の閉ループ）の方が床の違いに強い。
8. **安全の仕組みを先に作る。** 自動で強くしていくので:
   - 明示的な操作（UI シリアルのコマンドなど）でだけ始まる。Rock5A 未接続時の分岐に置かない。
   - 探索範囲の上限を固定（例: トルク上限 ≤ 3.2V）。安全停止（範囲外・向きのずれ・時間切れ）は必ず残す。
   - 1回ごとに一時停止し、人が位置を確かめて（必要なら置き直して）から次へ。オドメトリのずれが走行ごとに積み重なるため。
   - WheelUnit の状態バイト（過熱）と電池電圧を毎回記録し、閾値を超えたら中止。
9. **PC と機体のつなぎ方を決める**（8章の1）。

## 9. 最初の一歩（案）→ 8.1 の決定を受けて 10章の段階に置き換えた
1. 8章をユーザーと決める。
2. `parammeter.h` の調整対象の値を、`#define` から**実行時に書き換えられる構造体**（例: `VoltTuneParams`、既定値は今の値）に移す。ビルドは変わっても挙動は同じであることを床で1回確かめる。
3. 区間ごとの要約を計算して RAM に残す仕組みを作る（全サンプルの記録は RAM を約 62KB 使うので、複数回分は持てない。要約なら数回分入る）。

5. 残った値を、少ない回数の探索で決める。

## 10. 設計（機体の上で完結させる形）
### 10.1 全体の流れ（完成形、`src/control/auto_tune.c`）
```
IDLE ─(ST-Link で start_seq を書く)→ 10秒待つ（抜いて離れる）
 → 測る走行 → 15秒待つ → 確認1 ─合格→ フラッシュへ保存 → 終了（合格）
                         └不合格→ 0.2V 下げる → 15秒待つ → 確認2 … 最大3回 → 終了（不合格、前の値に戻す）
いつでも中止: テストの安全停止 / WheelUnit の過熱・電源異常ビット / 電池電圧の低下 / Rock5A の指令・緊急停止
             → 出力を止め、前の値に戻す
```
- **測る走行**（約1.5分）: 前・左・斜め2方向・その場旋回の5つの向きについて、トルク上限を 2.0→3.2V まで 0.2V 刻みで上げる。各段で原点から1.0mを往復する（旋回は ±π）。
  - このとき S字の加速度上限は高めにし、トルク上限が効く状態にする。
  - 各段の加速区間で、IMU の実際の加速度と新しいスリップ指標 S を測る。
  - 決め方: トルク上限 = 並進のすべての向きで S ≤ S_ref を満たす最大の段。`max_accel` = その段で実際に出た加速度（向きの中で最小）。`max_ang_accel` は旋回で同じように決める。
  - 向きごとの結果は RAM に残し、8章の5の判断に使う。
- **確認の走行**（約20秒）: 短くした動作パターンを、決めた値で1周走る。制約（8.1）を機体の上で判定する。テストの外側ループの想定減速度は固定の式（例: 0.9×`max_accel`）で決め、探索はしない（7章の2）。

### 10.7 ランプ試験（2026-09-24、床で未確認）— 3段階の走行と S_ref の較正を置き換える
- ユーザーの提案「電圧を3段階に分けず、なめらかに変えながらギリギリを判定したい」を受けて作った。**限界ギリギリの最高の加速度を狙う**（ユーザー）。余裕の比率は掛けない。試合の動きでギリギリが問題になるかは後で判断する。
- **考え方**: 超える分（center を超える電圧）はモータのトルクに当たる。そのトルク上限を、止まった状態から約0.2秒で 1.5V→3.6V まで上げて加速する（加速度の目標は十分高くして、上限＝実際のトルクにする）。
  - IMU の加速度が一番大きくなったときのトルクを**ピーク（＝限界として採用）**、車輪と IMU の加速度の差（進む向き）が 1.5m/s² を 20ms 超えた所を**滑り始め**として記録する。トルク上限にも IMU と同じ 15Hz の LPF を掛けて、位相をそろえて比べる。
  - 位置（オドメトリ）は判定に使わない（改善案4）。
  - 滑り始めを見つけたら 30ms ピークを拾ってから、トルクを7割に下げてブレーキへ。ブレーキも7割からランプで上げて、減速側を同じ方法で測る。
  - **止まった状態から短時間で上げる理由**: 速度が出ると center が増えて、電圧上限 4.9V までの余裕が減る（前進で約0.8m/s を超えると 3.6V をかけられない）。余裕がランプの値より小さくなったら「電圧の余裕なし」で打ち切る。
- **向きと回数**: 前・後・左・右・斜め4・その場旋回2 の10本。2本ずつ組（1本目は空きのある方へ、2本目は戻る向き）で、組ごとに低速で原点・向き0へ戻る。2回くり返し、ピークの差が 0.2V 以上か 10% 以上の向きの組だけ3回目（ユーザー案）。3回でも差が大きい向きは「不安定」。1本は約0.3〜0.5m、全体で約30〜40秒の見込み。
- **採用する値**（`tools/read_ramp_results.ps1` が計算して表示。機体の上での決定・保存は段階3以降）: トルク上限 = 並進8向きのピークの最小（くり返しの最小、3.2V 以下に収める）、加速度上限 = 並進8向きの IMU の加速度の最小、角加速度上限 = 旋回2向きの最小。
- 3.2V を超えるのはこの試験の中の一瞬だけ（ユーザー了承、上限 3.6V）。`VoltTune_Sanitize` は通さず、試験の定数で上限を持つ。
- **ファイル**: `src/control/ramp_test.h/.c`（状態機械、結果は RAM の `ramp_result`）、`auto_tune.c`（`test_id=2`）、`tools/read_ramp_results.ps1`。開始は `tools\autotune_start.ps1 -TestId 2`。波形は `tools\read_tcs_log.ps1`（`tcs_on` 列=何本目か、`target_vx` 列=フィルタ後のトルク上限 [mV]、10ms 周期、加速・ブレーキの間だけ）。
- **気づいたこと（未対応）**: `omni_drive.c` の電圧上限の扱い `allowed = 4.9 − |center|` は、ブレーキ（超える分が負）にも同じ余裕を使っている。実際にはブレーキ側は `4.9 + |center|` まで使えるので、速度が出ているときのブレーキのトルクを必要以上に絞っている可能性がある。ランプ試験のブレーキの結果（「電圧の余裕」で頭打ちになるか）を見てから判断する。

  1. **ピークの定義が壊れている**: 滑り始めを見つけたらランプを止める設計のため、「IMU の加速度が一番大きいトルク」は「滑り始め＋約0.3V」に切り詰められ、本当のピークを測っていない。波形では、滑り始めのあとも IMU の加速度は伸びていた（前 +x: 3.1→4.6m/s²）。

  4. 斜め（右前・左後）は、電圧の余裕（4.9V−今の回転数の電圧）が先に尽きて、滑り始めまで測れない本が多い。

- **次に直すこと（提案、ユーザー確認待ち）**: ランプを止めずに、IMU の加速度が落ち始める（または上限）まで上げ続ける／ランプをゆっくりにする（0.5秒程度）／3回目を測る基準をゆるめる（例: 0.3V か 15%）／旋回は速度の上限を上げるか、滑らないことを「上限以上」として記録する。滑り始め（車輪と IMU の離れ）を主指標にして、ピークは補助にする。

### 10.10 速度別の測定を追加（2026-09-24、実装済み・床で未確認）

- **走らせ方**（速度別の1本）: 始点へ低速で移動（0.8m/s）→ 助走（v0 まで、トルク上限 2.2V・加速度 3.0m/s² の滑らない範囲で巡航し、速度が v0 で加速度がほぼ 0 を 50ms 保つ）→ ランプ加速（目標速度は v0+2、打ち切りは v0+0.5m/s、または上限 3.2V、または電圧の余裕）→ ブレーキ（低速と同じ、弱い所から上げていく）→ 停止 → 次の本。速度の低い順に進む。
- **テスト範囲**（ユーザー決定、選択肢 C）: **前 3.5m・後ろ 1.0m・左右 2.5m**（原点はスタート位置）。安全停止の範囲は x: −1.0〜3.5m、y: ±2.5m（速度別の段を指定したときだけ。低速だけのときは従来の狭い範囲）。動作パターンのテストの範囲は変えていない。
- **範囲の予測**: 各本の前に、必要な長さ（助走＋ランプ＋ブレーキ）を予測し、範囲の端から 0.3m 内側に収まる経路（範囲の中心を経路の真ん中にする。+向きと −向きの組は同じ経路を往復する）だけを走らせる。同じ向きで低い速度の測定が済んでいれば、その距離を伸ばして予測する（助走とブレーキは速度の2乗、ランプは (v0+0.2) に比例）。**収まらない本は走らせずに「範囲不足」と記録する**（3.0m/s の前後は、最悪の場合の余裕が 0.15m と薄いので、2.0m/s の結果しだいで飛ばされる）。
- **記録**: `RampStrokeResult` を 40byte に拡張（助走の速度 v0、ブレーキ開始の速度、停止距離、加速距離、助走距離）。`RampRunResult` は 2260byte（最大56本）。波形のログ（10ms→速度別は 20ms 周期）は、速度別の測定を始めるときにリセットされる（低速のぶんは結果の表に残る）。
- **順序（推奨）**: まず `-Speeds 0,1,1.5,2`（斜め 1.5m/s を含む）→ 停止距離を見る → `-Speeds 3` を、左右から（実際は前後左右を一緒に走らせるが、予測が範囲不足と出た本は飛ばされる）。
- **初回の床走行（速度別、`docs/data/ramp_speed_20260924_run1_aborted.csv`）**: 低速の26本まで走り、速度別の最初の本（前 1.0m/s）のあと、障害物に当たって安全停止（28本目が巡航の時間切れ）。**そのため速度別の停止距離表は取れていない**（27本目のブレーキは 1.53m/s から 0.106m、平均減速度 11m/s² と出ているが、障害物に当たった記録で無効）。低速の結果は、これまでと同じ傾向（滑り始め: 前 1.9、後 2.1〜2.3、左 2.1〜2.3、右 2.1〜2.6、斜め 2.0〜2.9V）。
- **27本目から見つけた不具合を直した**: (1) 助走の距離が 0.88m と出ていた（1.0m/s なら約 0.2m）: 速度が v0 に着いたあとも、加速度が 0.7m/s² 未満という条件が満たされず巡航が続き、その分まで数えていた → 助走の距離は v0 に**最初に着くまで**とし、着いたと見なす加速度を 1.2m/s² にゆるめ、距離の予測に巡航の余裕（v0×0.3秒）を足した。(2) ランプ加速が、車輪の速度（オドメトリ）で打ち切られていた（空転すると実際より速く見えるため、1.0→1.5m/s を約0.06秒、加速距離 0.08m で終わった）→ 打ち切りの速度、ブレーキの開始速度、加速・ブレーキの距離を、**IMU の加速度の積分（機体の実際の速度）**で測る。ブレーキが終わるのは、車輪の速度が止まり、かつ機体の速度も 0.4m/s 未満になったとき。ランプ加速の最長は 0.6 秒。
- **速度別の2回目の床走行（`docs/data/ramp_speed_20260924_run2_aborted.csv`）**: 前後左右 1.0m/s の4本を走ったあと、5本目（斜め 1.5m/s）で障害物に当たって安全停止（巡航の時間切れ）。**4本のデータに、判定の誤りが見つかった**: (1) **加速の滑り始めが4本とも 1.9V**（＝ランプの開始 1.8V の直後）: 助走（トルクの差がほぼ 0）から急に 1.8V を掛けると、車輪だけ先に加速する過渡が出て、滑り始めと誤判定していた。(2) **ブレーキの滑り始めが4本とも 1.42V**（＝ブレーキのランプの開始点 0.7×1.9V の直後）で、同じ過渡の誤判定。そのあと、トルクを「見つけた値の7割」に下げるので、ブレーキが弱いまま止まった（1.1〜1.2m/s から 0.33〜0.49m、平均減速度 1.5〜1.8m/s²）。**低速の試験（v0=0）のブレーキの滑り始め（1.4〜2.3V、開始点の近く）も、同じ誤判定を含んでいる可能性がある。「ブレーキは加速より滑りやすい」という 10.8〜10.9 の結論は保留。**

- **速度別の3回目の床走行（エリア 3.5×2.5m、`-Speeds 1,1.5 -Rect 3.5,2.5 -Rotate`、`docs/data/ramp_speed_20260924_run3_aborted.csv`）**: 前後 1.0m/s の2本は範囲内で完了。3本目（左 1.0m/s）の助走の相で、ランプを始める条件（速度が v0±0.05m/s で IMU の加速度 1.2m/s² 未満を 50ms 保つ）が満たされず、v0 に着いたあとも約 1.9 秒巡航し続けて、y が 1.051m（範囲 ±1.05m）に達して安全停止（範囲外）。ぶつかってはいない。左右の助走は、v0 に着くまで 0.54m かかった（前後は 0.13〜0.15m）。2回目（90° 回して繰り返す）は未確認。

- **エリア 3.5×2.5m の長方形での使い方（ユーザーの環境）と、2回目の自動化**: `autotune_start.ps1 -TestId 2 -Speeds 1,1.5 -Rect 3.5,2.5 -Rotate`。
  - 置き方: 機体の中心を**エリアのど真ん中（対角線の交点）**に、**前を長辺に沿って**向けて置く（ユーザーの希望で、切りのいい位置にした）。`-Rect 3.5,2.5` は範囲を x: ±1.55m、y: ±1.05m（各端から 0.2m 内側）にする。2回目は、その場で右へ 90° 回るだけ（移動は要らない）。
  - `-Rotate`（`RAMP_SPEED_ROTATE`、mask の 0x80）: 1回目（機体の前が長辺に沿う）が終わると、機体が**自分で範囲の真ん中（原点）へ戻り、右へ 90° 回って**、範囲の縦横を入れ替えて（x: ±1.05m、y: ±1.55m）もう一度繰り返す（2回目）。機体の左（+y）が長辺に沿うので、左右の 2.0m/s は2回目で走る。低速（v0=0）は繰り返さない。結果の「回」の欄は、速度別の 1回目=1、2回目=2。
  - 2.0m/s は、範囲に収まると予測した本だけ走る（直線に約 2.5m 要る。1回目の前後、2回目の左右が収まる見込み）。最初は `-Speeds 1,1.5` で判定とブレーキを確かめ、そのあと `-Speeds 1,1.5,2`。
- **加速と減速のどちらが強いか**: 「減速のほうがやりやすい」という報告はある（ブレーキは逆向きの電圧が使えて余裕が増える、加速は高速で逆起電力で頭打ちになる。今の実装は逆にブレーキを絞っている）。**この機体の実測は、ブレーキ側の判定の誤り（上）が直るまで信頼できない。** 直した版の停止距離表（ブレーキを上限 3.2V まで上げて測る）で確かめる。
- **次**: 結果を見て、速度に応じた最大加速度・減速度（電圧の余裕から計算する連続な上限、ブレーキ側の余裕の修正を含む）を入れるか判断する（計画の手順1b）。試算では、ブレーキ側は今 3m/s で 4.9−|center|＝1.5V に絞られていて、実際の余裕は約 7.4V。
